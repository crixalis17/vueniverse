What is already strong

Evidence before AI

The model never invents the numbers. This is technically credible and easy to defend.

Event-conditioned health

Before, during, and recovery windows are more human than another daily wellness score.

Matched personal controls

Comparing the user with their own similar non-event periods is the strongest analytical choice.

Honest failure states

Demo labels, missing-data states, null results, and deterministic fallback create judge confidence.

Market reality

WellAware

Already links wearable and calendar data to find recurring health patterns.

Fulcra Timeline

Already merges health, calendar, and other personal data into an AI-ready timeline.

Risi

Already positions on-device AI, personal baselines, and health correlation detection as its value.

This validates demand, but removes the right to claim the broad concept as novel. The ownable wedge is event-level matched evidence plus a closed-loop personal test—not “AI understands your wearable.”

The full winning system begins here

Recommended positioning
“WhyPulse is a private personal-science engine: it finds repeated moments, shows what could disprove them, and learns whether one change alters your response.”

First target user: a knowledge worker with a wearable who feels drained by parts of the workday but cannot tell which repeated moments matter. The same evidence lifecycle expands to sleep, activity, illness, travel, media, and environment.

Make the existing event window the “Moment Fingerprint”

This is a visual treatment of the analysis already planned, not a new backend. Overlay repeated occurrences around the same event, show the matched baseline, then make recovery visible.

  • Six repeated traces, not one dramatic day.
  • Matched baseline in green, at similar times without the event.
  • Recovery duration becomes the memorable metric.
  • One null finding elsewhere proves WhyPulse can say “nothing repeatable yet.”

Implement “Test This” as the hero action loop

This is the missing user value. Observation alone can create anxiety; a small, bounded experiment gives the user a useful next step and a reason to return.

1 · DiscoverHeart rate rose before 6 of 8 recurring 1:1s.
2 · VerifyShow matched periods, exclusions, missingness, and unresolved influences.
3 · TestTry a 10-minute buffer before the next three 1:1s.
4 · LearnCompare the same event with and without the buffer using visibly labelled Demo Data.
The novelty claim to make: WhyPulse does not merely correlate or chat. It observes, fingerprints, challenges, explains, tests, learns, and proves—using one traceable evidence object throughout the full lifecycle.

The three-minute hackathon demo should still focus on one scenario so the story stays memorable.

Source scope rule: implement the product deeply before expanding the connector catalogue. Initial live sources are Health Connect, Android Calendar, Manual Check-ins, Multimodal Journal, and Demo Data. All other sources—including iOS—remain explicit expansion adapters. Novel features may use deterministic Demo Data for contexts whose live adapter is not yet included.
Initial live sources
  • Health Connect: heart rate, sleep, HRV when available, activity, steps, and workouts.
  • Android Calendar Provider: category, start, end, and recurrence; discard unnecessary title and identity data.
  • Manual Check-ins: caffeine, exercise, illness, mood, travel, and custom context.
  • Demo Data: deterministic histories that exercise every novel feature, failure state, experiment, and export.
  • Multimodal Journal: user-initiated photo and voice context on Android.
  • Encrypted local storage, background recomputation, migrations, pause, revoke, export, and delete.
Expansion sources later
  • Screen time/device activity and call timing.
  • Spotify, Strava, Discord/WhatsApp coarse activity, and direct wearable/ring APIs.
  • Smart Environment sources for air quality, light, temperature, and bedroom context.
  • FHIR record import and other clinical source adapters.
  • iOS, HealthKit, and EventKit.
  • Define their SourceAdapter contracts and Demo fixtures now; build live adapters only as expansion work.
Positioning rule
  • The initial Android source set must support the complete evidence lifecycle without depending on an expansion connector.
  • Integrations, local inference, generic chat, summaries, and cross-platform parity are not the novelty.
  • Do not market connector count, a generic timeline, or “digital twin” branding as the innovation.
  • Market the closed evidence lifecycle: Observe → Fingerprint → Challenge → Explain → Test → Learn → Prove.
  • No surface remains Preview or Coming later after its integration gate passes.

Implement every feature, but do not demo them as a checklist. Use one golden evidence bundle so the breadth feels like one system.

Definition of implemented

Complete means
  • Every listed feature is interactive and backed by real persisted domain logic.
  • Every enabled initial Android integration can consent, sync, pause, revoke, delete, and degrade honestly.
  • Every health number is deterministic and traceable to sources, analytical version, exclusions, and completeness.
  • Every model claim cites evidence and passes the frozen grounding and safety suite.
  • Android passes clean-install, permission-denial, offline, failure, migration, deletion, accessibility, and performance tests.
  • Clinician export uses separately reviewed safety wording and never turns the consumer app into a diagnostic product; live FHIR import remains an expansion adapter.
Not implemented
  • A static result screen, fake connector, dead button, or sample-only success path.
  • An expansion source presented as connected before its live adapter passes the source-compliance gate.
  • A Preview or Coming later label attached to a claimed novel feature.
  • A model doing hidden arithmetic, unrestricted database access, diagnosis, treatment, or unsupported causal reasoning.
  • A “Personal Digital Twin” that is only branding without versioned fingerprints, influences, experiments, and confidence.
  • Model adaptation without measurable improvement, regression gates, versioning, and rollback.
  • A deletion control that leaves derived evidence, explanations, digests, experiments, or exports valid.
Final scope rule: No novel product capability is removed because it takes longer. The current implementation is Android-only and uses the focused initial source set. iOS and difficult source adapters are explicit expansion work behind the same contracts.

Bottom line: build the complete private evidence lifecycle on Android: Context → Fingerprint → Challenge → Explain → Test → Learn → Prove. Health Connect, Android Calendar, Manual Check-ins, Multimodal Journal, and Demo Data are enough for the full product; harder sources and iOS plug in later through the same contracts.
