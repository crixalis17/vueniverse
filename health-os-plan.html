WhyPulse

The winning product is the complete evidence-to-action system: discover a pattern, replay it, challenge it, explain it, test a change, learn from the result, and preserve a trustworthy personal health history. Cross-platform parity and difficult connectors are expansion work, not requirements for this implementation.

Winning rationale

Scope decision

Core rule: a feature is core only when it advances one of the seven pitch stages and produces a visible user result. Everything else is Preview, Later, or removed.

Android only

One polished Android product. iOS is later.

Four primary sources

Health Connect, Android Calendar, Manual Check-ins, and deterministic Demo Data.

Evidence before language

Code computes every number. Models investigate and explain bounded evidence.

No duplicate concepts

Replay, influences, signal agreement, and provenance live inside the core journey instead of becoming separate products.

The seven-stage product journey

1 · DiscoverFind a repeated event-linked pattern.
2 · ReplaySee repeated traces before, during, and after it.
3 · ChallengeInspect controls, influences, contradictions, and missing data.
4 · ExplainRead a bounded, evidence-cited explanation.
5 · TestCreate one small personal experiment.
6 · LearnCompare the result and update the finding.
7 · PreserveKeep a traceable personal health history and proof.

Why it is core: Observe makes the ingredients of a finding tangible and earns trust before the “wow” moment. It leads directly to Today and the evidence lifecycle; it is not a generic endpoint dashboard.

Expansion later: screen time, calls, Spotify, Strava, Discord/WhatsApp coarse activity, direct ring APIs, environment, FHIR, and iOS. Expansion sources must use the same adapter contract and never expose content or identity unnecessarily.

Deterministic analysis

AnalysisRulesOutput
Recurring meeting → heart rateAt least four events; 15-minute pre-event, event, and 15-minute recovery windows; time-of-day controls; workout exclusions; completeness and influence checks.Effect range, occurrence count, consistency, recovery duration, unresolved influences, or “not enough evidence.”
Late activity → sleepDemo Data only until a live source is added; compare late-activity nights with matched nights; exclude illness/travel when logged.Sleep-duration difference, count, range, consistency, and uncertainty.
Personal experimentPredeclared change, required occurrences, adherence, missed-event handling, stop/cancel, same comparison rules.Supported, weakened, unchanged, or inconclusive update to the original finding.
Every number is code-generated. Medians, ranges, baseline differences, window counts, consistency, completeness, exclusions, possible influences, promotion gates, and provenance exist before any model call.

Bounded model role

RoleAllowedForbidden
ExplorerSelect one reviewed operation: compare repeated event, inspect recovery, or check a logged influence.Raw-history access, arbitrary queries, calculations, threshold changes, or finding promotion.
ExplainerExplain verified aggregates, cite evidence IDs, state uncertainty and unresolved influences.Diagnosis, prescription, healthy/unhealthy labels, causality, invented numbers, or unsupported advice.
Ask WhyPulseAnswer “Why?”, “What could weaken this?”, and “What should I observe next?” for one evidence bundle.Generic health chat or access to the complete personal timeline.

MedGemma never receives calendar titles, identities, message text, phone numbers, arbitrary raw records, or the complete timeline.

Fallback ladder

  1. Phone-local MedGemma when latency, memory, and thermal behavior are stable.
  2. Clearly labelled development-machine MedGemma using Demo Data only.
  3. Deterministic evidence summary when no model runtime is reliable.

GPT-5.6 and Codex

Build-time only: fictional histories, adversarial cases, evaluation, implementation, debugging, and submission evidence. The Android app has no GPT key, SDK, endpoint, request path, or personal-data flow.

Runtime flow

Sources / ObserveIngest, normalize, then show the 30-day source rhythm
TimelineNormalize, dedupe, encrypt, preserve provenance
AnalyzeWindows, controls, influences, gates
EvidencePromote or return no finding
ExplainBounded model plus output guard
ExperimentProtocol and measured comparison

Maintain a fixed rolling 30-day window. New or deleted records recompute only affected windows. Live and Demo records use separate namespaces and are never silently mixed.

Build gates

GateMust be true
1 · Data spineFocused sources enter the encrypted local timeline with consent, normalization, dedupe, provenance, deletion, Demo reset, and 30-day recomputation; Observe renders only that active store with privacy-safe labels.
2 · Discover / Replay / ChallengeThe meeting analysis produces a Moment Fingerprint and inspectable Evidence; positive, null, contradictory, and missing-data fixtures pass without a model.
3 · ExplainExplorer stays allow-listed; explanation cites evidence; guard blocks unsupported output; all fallback modes are labelled.
4 · Test / LearnA user creates, completes, cancels, or fails an experiment and the original finding updates honestly.
5 · Preserve / ReleaseHistory, deletion invalidation, Proof / Export, offline behavior, clean Android install, accessibility, and three consecutive demo runs pass.

Definition of done

  • The full seven-stage journey works on Android from a clean install.
  • Health Connect, Android Calendar, Manual Check-ins, and Demo Data work independently.
  • Observe accurately reflects the active store, refreshes after mutations, exposes accessible chart summaries, and never reveals discarded Calendar identity.
  • The meeting analysis passes positive, null, contradictory, missing-data, timezone, duplicate, and deletion tests.
  • Every displayed number opens traceable evidence.
  • Model output cannot add numbers, diagnosis, treatment, causality, or health verdicts.
  • One experiment can be created, completed, cancelled, and resolved inconclusively.
  • History preserves versions and invalidates results when source data is deleted.
  • Live, Demo, phone-local, development-machine, fallback, unavailable, Preview, and Later states are honest.
  • The three-minute demo succeeds three consecutive times.
Canonical product rule: if a capability does not help the user discover, replay, challenge, explain, test, learn, or preserve, it is not part of the core WhyPulse build.
